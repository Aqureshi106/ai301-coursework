# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | the environment record in the repro report (its `Environment:` line or the equivalent sentence), read against the environment the issue states and the `bug reports:` template asks in the repo-facts block | Pass if the report names the version of the software under test and the OS/platform it ran on, plus any further identifier this issue's failure turns on (build profile, install method, shell, driver); and if any of those differ from the issue's, the report says so itself. A package with no environment record anywhere fails, however good its artifact | required |
| steps-rerunnable | the steps, commands, and inputs in the repro report, read against the reproduction the issue gives | Pass if a stranger holding that environment could arrive at the same run from what the package shows: the starting state is named, the exact command is given, and every input the run depends on is shown inline, publicly fetchable, or described precisely enough to rebuild without guessing. A step resting on something only the author has (a private repo, an unshared internal config, "set up the project") fails, and so does an input whose exact content decides the failure when it is neither shown nor reconstructible | required |
| artifact-matches-issue | the artifact in the repro report (output excerpt, log, screenshot), compared line by line with the failure the issue reports: its error text, its exit code, and its failure class (panic vs handled error vs silent no-op) | Pass if the artifact shows the failure the issue names, not merely a failure in the same area; or the report states plainly that it did not reproduce and shows what it got instead. An artifact showing an adjacent error, a different exit class, or only that the tool ran, fails; so does a package that shows no artifact at all | required |
| claim-matches-evidence | every assertion of outcome in the repro report's conclusion and in the claim comment ("reproduced", "confirmed", "on both versions", "ran it ten times", a named cause), checked against the artifacts the package actually shows | Pass if the assertion the package rests on — that the issue's failure did or did not occur here — is backed by an artifact shown in the package, and no assertion overstates what that artifact shows. Supporting observations (a repeat count, a described control, a variant run) may stand in prose when the outcome does not rest on them. An evidenced cannot-reproduce passes. A "reproduced" or "verified" with no artifact behind it, or a root cause stated as established fact without one, fails | required |
| claim-is-specific | the claim comment, read against the issue it is posted on | Pass if the claim names something only this issue has (its version and its behavior, or the artifact below it) and states a next action the author controls. A comment that would fit any other issue unchanged, a bare +1, or a promise of a fix, a merge, or a date, fails | required |
| ai-policy-respected | the `contribution policy` line in the repo-facts block (and any AI policy it names), read against the text of both comments; the package's comments count as AI-assisted work, which is this course's workflow | Pass if that policy states no disclosure requirement, or states one and at least one of the two comments names the AI assistance and its extent. A policy that asks only for human understanding, human responsibility, or comments written by a human in their own words is not a disclosure requirement: pass it when the comments read as a person's own words rather than generated prose | required |
| control-run | a second run shown beside the failing one in the repro report: the same command off the trigger, the neighbouring input that works, or the version or config where the behavior differs | Pass if the report shows a run that isolates the trigger rather than only the failure | preferred |

## Verdict rule

Accept if every required check passes. Preferred checks never change the verdict; they only separate a strong package from a sufficient one. If any required check fails, reject. Grade a check `unclear` only when the evidence it names is genuinely absent from the package, and count `unclear` as fail for the verdict: proof a stranger cannot verify is proof that is not ready to post.
