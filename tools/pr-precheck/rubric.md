## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| diff-within-plan | The diff's changed files and hunks (eval: the Candidate PR's Diff; live: `git diff main...HEAD`), read against the plan's Files line, its in-scope and not-in-scope statements, and any deviation or known-limit note (eval: the Plan context block; live: `plan.md`), and against the artifacts the repo's stated asks require. | Pass if every changed file and every hunk is licensed: it falls inside what the plan's scope and Files line name, or inside a deviation note recorded in the plan, or it is an artifact the plan or the repo's stated asks call for (a test for the fix, a changelog or whatsnew entry). Fail if the diff does something the plan never named and no recorded deviation note covers it: a new flag, option, or setting, a rename or rewrite pass, reworded unrelated text, an edit to a file or function outside the plan's boundary, or anything the plan's not-in-scope line excludes. An extra that is mentioned only in the description and not in the plan is still unlicensed. Unclear only if the plan states no scope or Files line to compare against. | required |
| plan-delivered | Each deliverable the plan promises (every file or area in its Files line and every named or numbered change in its scope statement), read against the diff's hunks, plus the plan's deviation or known-limit note and the description's statement of what the PR leaves out. | Pass if every promised deliverable has a hunk in the diff, or its absence is disclosed: the plan records the deferral or limit in a deviation or known-limit note, or the description names what the PR leaves out and why. A disclosed shortfall is honest work and passes. Fail if a promised piece (a code change, a docs update, a test, a second fix) is missing from the diff and nothing discloses it, or if the diff never implements the plan's change at all. Unclear only if the plan states no deliverables to compare against. | required |
| description-matches-diff | The claims the PR title and description make about what the PR contains or leaves out (fidelity phrases such as "exactly as planned", "in full", "no changes beyond the plan"; named deliverables such as docs, tests, or a changelog entry; named behavior changes), each read against the diff and the test evidence. | Pass if every such claim is true of the diff: the hunk it names exists, and nothing it denies is present. When the description makes a fidelity claim, that claim is false if diff-within-plan or plan-delivered failed. Fail if the description claims a deliverable the diff lacks, denies a change the diff contains (for example "no changes beyond the plan" over an unplanned hunk), or describes a behavior change the diff does not produce. Process claims the package cannot show (such as "code formatted" or "guidelines read") are not failed for lack of proof; they fail only if something in the package contradicts them. Unclear only if the package has no description. | required |
| decisive-test-evidence | The test evidence, read against the plan's test plan and the repro evidence's steps and recorded before-result (eval: the Plan context block and the Candidate PR's Test evidence; live: the test plan in `plan.md`, the repro, and `test_evidence.md`), plus the tests the diff adds. | Pass if the evidence shows the plan's repro (or a named equivalent) run on the branch with the observed after-result for the behavior the plan said would change, set against the before-result (shown, or the repro's recorded one) so the change is visible; and each distinct failure mode or scenario the plan's test plan names by name is shown or disclosed as not run; and any test the PR adds would fail without the fix, so it exercises the fix and not only the unchanged path. A control the plan lists need only be reported as unchanged, not transcribed. Fail if the evidence is "tested locally", "works on my machine", or "tests pass" with no observable named; if it exercises only the unchanged path or a control; if the plan's repro is never re-run; if the test plan names a second failure mode the evidence never touches; or if an added test checks something other than the fix. Unclear only if the package has no test evidence at all. | required |
| repo-checks-run | The test evidence's account of the repo's own checks, read against the test command or smoke check the plan's test plan names (or, if it names none, the test command the repo's PR template or contributing docs name). | Pass if every repo test command or smoke check the plan's test plan names (or, if it names none, the repo's stated test command) is shown run on the branch with its outcome stated (passes, a pass count, or the specific failures), and that run includes the code the diff changed. If neither the plan nor the repo names a check beyond the repro itself (for example a one-line config change), pass when the checks the plan does name are shown run with their outcome, or when there is no repo check to run; the repro itself is graded by decisive-test-evidence. Fail if a named command or suite is never shown as run, if a one-off script stands in for it, or if its outcome is missing or failing. Unclear only if the package has no test evidence at all. | required |
| diff-reviewable | Every hunk of the unified diff (eval: the Candidate PR's Diff; live: `git diff main...HEAD`), with the commit list as corroboration only. | Pass if every hunk is the fix, a test for it, or an artifact the plan or the repo asks for, so a reviewer can see the change without digging past noise. Fail if the diff carries debris: debug prints or logging left in, commented-out code, dead or unused functions or imports the change added, TODO or WIP leftovers, formatting, re-indent, or import-reorder churn, identical lines printed twice, or a hunk unrelated to the fix. A comment that explains what the fix does or why is not debris. Commit messages such as "wip" or "misc cleanups while debugging" corroborate debris the diff shows but never fail a clean diff on their own, and a clean history never excuses debris in the diff. A hunk that is both unplanned behavior and noise fails this check and diff-within-plan both. Unclear only if the package has no diff. | required |
| template-and-asks | The repo's stated PR asks (eval: the Repo facts block's `pull requests` line; live: the repo's PR template and `docs/CONTRIBUTING.md`, plus the house rules in `scope.md`, which treat the template as always used), read against the PR description and the diff. | Pass if every ask the repo states is met with real content: each template section or checklist item is present and filled in for this PR (not blank, not copied boilerplate, not "n/a" with no reason), the issue-closing line the repo asks for is present, and every artifact an ask requires (tests with the fix, a changelog or whatsnew entry) is in the diff. A short, accurate fill-in meets an ask; length is not the test. Pass if the repo states no PR asks. Fail if any stated ask is visibly ignored: a required section empty or absent, the checklist missing, the closing line absent, or a required entry missing from the diff. Unclear only if the package does not show what the repo asks. | required |
| disclosure-policy | The repo's stated AI-use policy (eval: the Repo facts block's `contribution policy` line; live: `docs/CONTRIBUTING.md` and the PR template), read against the PR description. Treat every package as AI-assisted work. | Pass if the repo states no AI policy (silence is permission, not a requirement to invent a disclosure), or states one and the description itself meets it: where the policy requires disclosure, asks for human-written text, or asks the author to understand the work, the description names the AI assistance (the tool and what it did) and says, as asked, that the text is the author's own and the change is understood. A policy that only welcomes AI help and asks for nothing needs nothing. Fail if the policy asks for a disclosure or statement and the description has none. Unclear only if the package does not show the repo's policy. | required |
| thread-direction | Explicit direction or a question from a maintainer or member in the thread highlights (live: the issue's thread), read against the plan and the description. | Pass if no maintainer gave explicit direction or asked a question the PR must answer, or the plan or description engages it: follows it, or says why not with evidence. Fail if a maintainer's explicit direction or open question is ignored or contradicted. Unclear if the thread is not in the package. | preferred |
| limits-disclosed | The limits, deferrals, and soft spots the plan records, read against the description's statement of what the PR does not do. | Pass if the description restates any limit or deferral the plan records, or names the one thing a reviewer should weigh, so a reader can weigh the shortfall; or if the plan records no limit and the diff shows none. Fail if a limit the plan records is absent from the description. | preferred |

## Verdict rule

Accept (ready to submit) only if every `required` check passes. A
`fail` on any `required` check rejects (holds) the package. `preferred`
checks are recorded but never change the verdict; they only separate a
strong PR from a sufficient one.

Grade a check `unclear` only when the evidence it names is genuinely
absent from the package (for example, no test-evidence section at all).
If the evidence is present but does not meet the pass condition, the
grade is `fail`, not `unclear`. An `unclear` counts as a `fail`: if the
package does not let a reader verify a required check, the PR is not
ready to submit, so a required check graded `unclear` also rejects.

A shortfall that is honestly disclosed is not a failure by itself. A PR
that does less than the plan and says so (in a deviation note or in the
description, naming what is left out and why) can accept; a PR that
does less, or more, and says nothing cannot. Do not reject a package
for being terse, for having one commit, or for doing less than
everything: reject it only when a required check fails or cannot be
verified.
